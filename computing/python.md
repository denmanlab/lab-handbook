# Python | Computing

The Denman Lab primarily uses python, except for a few specialized bits of MATLAB code (mostly run on data acquisition machines). We also highly encourage the use of jupyter notebooks for code prototyping and analysis. The suggested analysis suite is

 - An environment manager (Anaconda) to [set up a dedicated python environments for tasks][1]. Make sure you download the python3 installer, you can always make an python2 environment with this if it ever becomes necessary.

Installation instrcutions for setting up jupyter lab and Python 3 with Anaconda are below. VS code is stand alone and can be installed following the instructions on the VS code website. 

## Installation
1. [download][3] and [install][4] Anaconda. 
2. Open a Terminal (Mac OS X) or the newly installed Anaconda command prompt (Windows). 
3. create a new environment. you should name your envirornment something short and informative about what it will be used for, e.g.: <br>```conda create -n name_of_your_environment``` 
4. from your terminal [activate your newly created conda environment][5]:<br>
`conda activate name_of_your_environment`

`conda install pip`<br>
`conda install -c conda-forge jupyterlab`<br>

7. Start a jupyter server by entering `jupyter lab` and you are ready make a new ipynb notebook or find one you have downloaded.

# SpikeGLX Data Preprocessing  
In each recording, there are multiple data streams - One from the NI device, and one for each probe.   Each device streams samples of data to the acquisition software at a rate that is unique to each device and its internal clock. Because of this, spike times are not _exactly_ synchronized to stimulus timestamps, and spike times from multiple probes are not _exactly_  synchronized to each other. To solve this, SpikeGLX provides the companion tools **CatGT** and **TPrime** to synchronize all data down to sub-milisecond accuracy. 

During the recording, a 1Hz common sync pulse is generated by imec slot 3 on the Neuropixels box. All probes will automatically record the sync wave on **bit 6 of the SY channel (Ch. 385)**. The sync pulse is also streamed to the NI device on **digital bit 7**. Despite each device having different sampling rates, all files have a common start time (T0). 

**ENSURE THESE SETTINGS ARE CORRECT IN THE SYNC TAB BEFORE ANY RECORDING**

## Extracting sync wave edges (CatGT)
CatGT can perform several post-processing jobs, but for our purposes, we generally only extract sync waveform edges to use as TPrime inputs. These output for each stream is a .txt file with edges reported in seconds (NOT SAMPLES). 
There are 3 extractor types:
 - Probe (SY)
 - Digital Channels (XD)
 - Analog Channels (XA)

In our recordings, the NI device records the sync wave on digital bit 7, so we can ignore XA. While both CatGT and TPrime are command line tools, you can easily edit the `runit.bat` file for each and change parameters for each run. Parameters are as follows:
* dir=D:\
    - This is the directory for the recording files. If you're running this program on the acqusition computer, the files should still be on the D: drive were they were acquired to. 
* run=run_name
    - the run name includes the entire name of your folder/files before g or t indices
* g=0
    * The 'g-index' or 'gate-index' corresponds to each recording epoch following you clicking `Enable Recording`. Unless you had to click that button multiple times, there should only be one recording epoch (i.e. g=0).
* t=0
    * SpikeGLX can write multiple files within a gate epoch based on a TTL trigger. For our recordings, this will always be 0. 
* -ap -ni
    * These parameters indicates the _types_ of streams to extract sync edges from. If you also want to align LFP data, use -lf.
* -prb\_fld -t\_miss-ok
    * These inputs ensure that CatGT will read data in a probe-per-folder manner, and silently skip probes that are missing.
* -XD=8,7,500
    * this will remain the same unless the NI digital bit for the sync pulse is changed. The numbers indicate the zero-based word (8), bit (7) and minimum pulse length in msec (500)
* -SY=_probe#_, -1,6,500
    * There will be an SY input per probe. The inputs begin with the number of the probe (zero-based). The other inputs are the same as the XD channel (probe, word, bit, length).

Here is an example code to run CatGT for a three-probe recording in our system using the `runit.bat`:
```
set LOCALARGS=-dirD:\ -run=20211022_example -g=0 -t=0 -ap -ni -prb=0:2 ^
-prb\_fld -t\_miss\_ok ^
-XD=8,7,500 -SY=0,-1,6,500 -SY=1,-1,6,500 -SY=2,-1,6,500
```
Output files are named using a common format:
* run\_g0\_tcat.imec0.ap.SY\_word\_bit\_millisec.txt
* run\_g0\_tcat.nidq.XD\_word\_bit\_millisec.txt

### Parsing Stimulus/Event Timestamps
Like the sync pulse, timestamps from the stimuli and eyetracking system are recorded as binary (up/down) points on digital lines in the digital channel from the NI stream. To extract these timestamps, use the `parse_ni_digital` function from the `sglx_analysis` package in `dlab`. The output of this function is a dictionary with an array of timestamps for each digital line. Save each line of interest to an individual numpy array to use as a TPrime input. 
```
import dlab.sglx_analysis as sglx

#Parse digital channel from .bin file into timestamps for each line
dlines_rising,dlines_falling = sglx.parse_ni_digital(recording_folder)

#Save out each lines timestamps as a numpy array
np.save(dlines_rising[key],'output_file_name.npy')

#Plot the timestamps
sglx.nidq_plot(dlines_rising)
```
### Converting Spike Times to Seconds
TPrime requires all input files to list times in seconds, not sample numbers. Unfortunately, the Kilosort output `spike_times.npy` repots times in sample numbers. To fix this, all you need to do is divide the array by the probe's sampling rate. Neuropixels sample data at roughly 30kHz, but there will be individual variation between recordings. The `sglx_analysis` package in `dlab` contains helper functions to use accurate sampling rates. 
```
import numpy as np
import os
from dlab import sglx_analysis as sglx

probe_path = '...\\recording_name_g0_imec0\\'
spike_times = np.load(os.path.join(probe_path,'spike_times.npy'))
meta = sglx.readAPMeta(probe_path)
sampling_rate = float(meta['imSampRate'])

spike_seconds = spike_times/sampling_rate

np.save(spike_seconds,os.path.join(probe_path,'spike_seconds.npy')

```

## Aligning timestamps to a common source (TPrime)
Once you've extracted sync pulse times and parsed all relevant timestamps for analysis, you can then use TPrime to align all timestamps to a common clock. TPrime uses three types of inputs to do this. 
* `tostream`: This is the file containing sync wave times (CatGT output) from the reference stream which you will align all other times to. The choice is arbitrary, but we generally use probe A (imec0).
*  `fromstream`: These are the sync wave times from all other devices whose timestamps you'd like to align (Probes and NI device). Each `fromstream` is identified by an arbitrary positive integer which is then matched to events files. 
*  `events file`: These are the actual timestamps which you are aligning.
    * Times must be in seconds (**NOT SAMPLE NUMBERS**) 
    * Times are relative to start of file
    * Times are in ascending order
    * Acceptable input/output file types are .txt and .npy  

Like CatGT, TPrime is a command line tool that can be run using a `runit.bat`file. Below is an example of inputs for a 3 probe recording with timestamps from digital lines 1-3.
```C++
> TPrime -syncperiod=1.0 ^
 -tostream=D:/recording_name_g0/recording_name_g0_imec0/recording_name_g0_tcat.imec0.ap.SY_100_6_500.txt ^
 -fromstream=1,D:/recording_name_g0/recording_name_g0_imec1/recording_name_g0_tcat.imec1.ap.SY_384_6_500.txt ^
-fromstream=2,D:/recording_name_g0/recording_name_g0_imec2/recording_name_g0_tcat.imec2.ap.SY_384_6_500.txt ^
-fromstream=3,D:/recording_name_g0/recording_name_g0_tcat.nidq.XD_8_7_500.txt ^
-events=1,D:/recording_name_g0/recording_name_g0_imec1/spike_seconds.npy,D:/recording_name_g0/recording_name_g0_imec1/spike_seconds_adj.npy ^
-events=2,D:/recording_name_g0/recording_name_g0_imec2/spike_seconds.npy,D:/recording_name_g0/recording_name_g0_imec2/spike_seconds_adj.npy ^
-events=3,D:/recording_name_g0/d1_rising.npy,D:/recording_name_g0/d1_rising_adj.npy ^
-events=3,D:/recording_name_g0/d2_rising.npy,D:/recording_name_g0/d2_rising_adj.npy ^
-events=3,D:/recording_name_g0/d3_rising.npy,D:/recording_name_g0/d3_rising_adj.npy ^
```

# spike sorting
Generally, the lab uses [Kilosort2][10] with [phy][11] to sort Neuropixels data into times of spikes from individual neurons. [SpikeInterface][12] is currently being explored as an alternate means of automated sorting. 

To begin, follow installation instructions for [Kilosort2][13] and [phy][14]. This has already been done on the Neuropixels acquistion PCs in the lab. 

The workflow consists of two parts:
1. automated sorting with [Kilosort2][15]
2. manual refinment and annotation with [phy][16]

(1) To use Kilosort in the lab:

 - It is recommended that you run kilosort on data stored on the NVMe drive in the acquisition computer (D: on EphysRig1), it will run signifiantly faster.
 - **copy** configFile384, master_kilosort, and neuropixPhase3B1_kilosortChanMap into the folder where your raw data lives.
 - in MATLAB, ```cd``` to change the working directory to the folder where you just put these files. **IMPORTANT**: you want to copy these files, not move them. This allows every run of Kilosort to have a record of what was run. You can find these in a previously sorted folder, or in C:\Users\denma\Documents\Kilosort2\configFiles and C:\Users\denma\Documents\Kilosort2\
 - in MATLAB, run ```master_kilosort```

(2) To use phy in the lab:
- open an Anaconda prompt and enter ```conda activate phy2b```
- ```cd``` to the location of your sorted data
- run ```phy template-gui params.py```
